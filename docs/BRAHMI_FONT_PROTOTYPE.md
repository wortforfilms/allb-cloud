# MAATAA Brahmi Sans — a prototype font, HarfBuzz-verified

Status date: 2026-09-12. Prompted by a gap found while explaining
`maataa_shell`: `brahmi_tokenizer.rs` produces correct UTF-8 for the full
Brahmi block (U+11000–U+1107F), but almost no installed terminal font has
glyphs for that block, so the output was rendering as tofu boxes.

## What this is, and what it is not

This is **not** a reproduction of historical/epigraphic Brahmi letterforms.
Reconstructing Ashokan-era glyph shapes accurately requires a type designer
working from epigraphic sources — that is a real specialist skill, and
guessing at it from memory risked misrepresenting a real ancient script.

What was built instead is an **original geometric typeface**, generated by
a small Python script (`build_font.py`, committed alongside the font) using
`fontTools`. Every one of the 128 code points in the Brahmi block gets a
real, filled, distinct glyph, built from six primitives (stem, bar, hook
left/right, loop, diagonal, dot) combined by a deterministic rule keyed to
the code point's index — the same input always produces the same shape.
Independent vowels and consonants (U+11003–U+11037) are drawn full-height
with a left stem; every other code point in the block (signs, vowel-signs,
punctuation, numbers, digits) is drawn smaller and stem-less, so it reads
visually as a "mark" rather than a full letter.

If a task ever needs scholarly-accurate Brahmi — publishing, academic use,
anything user-facing — the honest answer is **Noto Sans Brahmi**, not this.
This font's job is narrower: give the MAATAA dev tools a real, installable
font so `maataa_shell` output is legible glyphs instead of empty boxes.

## Where HarfBuzz actually comes in

HarfBuzz is a text-*shaping* engine, not a font-design tool — it doesn't
draw glyphs, it takes a font's existing glyph/OpenType data and lays text
out correctly. So it's used here as the **verification layer**, not the
design tool: `test_shaping.py` runs the real HarfBuzz library
(`uharfbuzz`, HarfBuzz 14.4.0) against the finished font and confirms every
one of the 128 Brahmi code points shapes to a real glyph — zero `.notdef`
fallbacks — across the independent-vowel/consonant range, the sign range,
and a full sweep of the entire block.

```
vowel a + consonant ka + consonant ma: 3 chars -> 3 glyphs, .notdef count = 0
candrabindu + anusvara + visarga: 3 chars -> 3 glyphs, .notdef count = 0
full run across the block: 128 chars -> 128 glyphs, .notdef count = 0
```

No OpenType GSUB/GPOS rules are defined (no mark-to-base attachment, no
reordering) — each code point is an independent advance-width glyph. That's
a real simplification versus production Indic text layout. It matches the
WASM exports in `lib.rs` (`tokenize_brahmi_script`), which treat each code
point as an independent token. The canonical `brahmi_tokenizer.rs` groups
aksharas, but the font does not shape them.

## Files

- `assets/fonts/MAATAA-Brahmi-Sans.ttf` — the font, installed into
  `~/Library/Fonts` on this Mac so Terminal.app/iTerm2 pick it up via
  automatic font-fallback for any Brahmi code point missing from the
  active terminal font. No terminal settings change needed for Terminal.app;
  iTerm2 users who want to force it can set it as the "non-ASCII font" in
  Profiles → Text.
- `assets/fonts/build_font.py` — generates the font from scratch (pure
  Python, `fontTools`, no external font-editor dependency).
- `assets/fonts/test_shaping.py` — the HarfBuzz verification script above.
- `assets/fonts/preview.png` — a rendered grid of vowels, consonants,
  marks and digits for a quick visual sanity check.

## Honest limitations

- Glyph shapes are an original design, not paleography — say so if this
  ever surfaces outside internal dev tooling.
- No mark positioning/reordering (GPOS/GSUB) — fine for `maataa_shell`'s
  one-token-at-a-time output, not sufficient for real running Brahmi text.
- Installed for this one Mac user account only — not packaged or signed
  for distribution.
